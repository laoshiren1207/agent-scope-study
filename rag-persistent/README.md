# RAG 持久化

## 前言
比如一份客服手册包含多个章节，可以先按标题拆开：
```text
客服手册.md
├─ 退款政策 → 文本块 1 → 向量 1
├─ 退货政策 → 文本块 2 → 向量 2
└─ 物流政策 → 文本块 3 → 向量 3
```
查询时检索这些文本块，并保留它们来自哪个文件、哪个章节的信息。这样回答引用资料时，就能找到原始出处。

### 表结构
我们使用`pg-vector` + `mp4`配合`agentscope-java`来做
```sql
CREATE EXTENSION IF NOT EXISTS vector WITH SCHEMA public;

CREATE TABLE IF NOT EXISTS public.kb_chunk (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    knowledge_base_id bigint NOT NULL,
    document_id bigint NOT NULL,
    document_version integer NOT NULL DEFAULT 1,
    chunk_no integer NOT NULL,
    title text,
    content text NOT NULL,
    content_hash varchar(64) NOT NULL,
    token_count integer,
    source_uri text,
    source_locator jsonb NOT NULL DEFAULT '{}'::jsonb,
    metadata jsonb NOT NULL DEFAULT '{}'::jsonb,
    embedding_profile varchar(128) NOT NULL,
    embedding_model varchar(128) NOT NULL,
    embedding public.vector,
    embedded_at timestamptz(6),
    status varchar(16) NOT NULL DEFAULT 'pending',
    error_message text,
    created_at timestamptz(6) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at timestamptz(6) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted_at timestamptz(6),
    CONSTRAINT uk_kb_chunk_version UNIQUE
        (tenant_id, knowledge_base_id, document_id, document_version, embedding_profile, chunk_no),
    CONSTRAINT ck_kb_chunk_position CHECK (document_version > 0 AND chunk_no >= 0),
    CONSTRAINT ck_kb_chunk_content CHECK (btrim(content) <> ''),
    CONSTRAINT ck_kb_chunk_hash CHECK (content_hash ~ '^[0-9a-f]{64}$'),
    CONSTRAINT ck_kb_chunk_json CHECK
        (jsonb_typeof(source_locator) = 'object' AND jsonb_typeof(metadata) = 'object'),
    CONSTRAINT ck_kb_chunk_vector CHECK (embedding IS NULL OR public.vector_norm(embedding) > 0),
    CONSTRAINT ck_kb_chunk_ready CHECK
        (status <> 'ready' OR (embedding IS NOT NULL AND embedded_at IS NOT NULL)),
    CONSTRAINT ck_kb_chunk_token_count CHECK (token_count IS NULL OR token_count > 0),
    CONSTRAINT ck_kb_chunk_status CHECK (status IN ('pending', 'ready', 'failed', 'archived'))
);

CREATE INDEX IF NOT EXISTS idx_kb_chunk_search_scope
    ON public.kb_chunk (tenant_id, knowledge_base_id, embedding_profile)
    WHERE status = 'ready' AND deleted_at IS NULL;
```

这张表的核心设计是：一行保存某个文档版本中的一个片段，以及该片段在某套向量配置下的处理结果。

例如，一份《售后政策》分成“退款”“退货”“发票”三个片段，就会保存三行数据。

| 信息类别 | 主要字段 | 作用 |
|---|---|---|
| 归属与位置 | `tenant_id`、`knowledge_base_id`、`document_id`、`document_version`、`chunk_no` | 确定片段属于谁、哪个知识库、哪份文档、哪个版本，以及排列位置 |
| 片段正文 | `title`、`content`、`content_hash`、`token_count` | 保存实际用于向量化、提供给大模型的内容，以及内容指纹和 Token 数 |
| 来源与业务属性 | `source_uri`、`source_locator`、`metadata` | 记录原文地址、页码或章节位置，以及标签等扩展属性 |
| 向量与配置 | `embedding_profile`、`embedding_model`、`embedding`、`embedded_at` | 保存向量、生成配置和成功时间，支持相似度检索 |
| 处理状态 | `status`、`error_message` | 记录正在处理、可检索、失败或已归档，以及失败原因 |
| 数据生命周期 | `created_at`、`updated_at`、`deleted_at` | 记录创建、更新时间，并支持逻辑删除 |

其中几个设计值得重点理解。

1. 文档和片段分开标识

document_id 是文档的稳定业务 ID；`chunk_no` 是该版本内从 0 开始的片段序号。

这样检索命中第 5 个片段后，还可以找到同一文档、同一版本的第 4、6 个片段，补充上下文。

2. 用版本保留文档变化

原文、解析方式或分块规则变化后，增加 document_version，重新生成片段。

这样可以保留旧数据，支持追溯；新版本确认可用后，再归档旧版本。版本号本身不会自动让旧版本退出检索。

3. 把向量配置单独记录

embedding_model 记录服务暴露的模型名；`embedding_profile` 标识实际模型版本、维度及预处理规则。

相同模型名背后的配置可能变化，所以检索需要限定 profile，确保查询向量和片段向量来自相同配置。

4. 正文和向量一起保存

embedding 用于计算“哪些片段与问题相近”；`content` 则是在召回后交给大模型的参考原文。

source_uri 和 source_locator 用于回答后的来源引用，例如定位到某份 PDF 的第 12 页。`metadata` 则保存标签、分类、语言等业务信息。

5. 状态支持分阶段入库

片段先保存为 pending，向量生成成功后变成 ready，失败则记录为 failed。

表中的约束要求：ready 必须同时具备向量和向量生成时间，避免未完成的数据进入检索。

最后，唯一约束：
```text
tenant_id + knowledge_base_id + document_id + document_version + embedding_profile + chunk_no
```

保证同一范围内，同一文档版本、同一向量配置的同一位置只保存一条记录。`id` 是这条记录的数据库主键；`content_hash` 是内容指纹，当前没有对它设置唯一约束。

### 配置文件

这里特别说一点，配置文件中有一个 `profile`相关字段。他的作用是我们给一套固定的向量生成规则起的名字。它由应用自己定义，用于标记和筛选数据库中的向量。

```yaml
rag:
  embedding:
    model: Qwen3.5
    dimensions: 4096
    profile: qwen35-4096-raw-v1
```
这个名字表达的约定是：

| 名称部分 | 含义 |
|---|---|
| `qwen35` | 使用约定的这一个实际模型版本 |
| `4096` | 输出 4096 维向量 |
| `raw-v1` | 使用第 1 版正文预处理规则 |

为什么需要它？因为查询问题的向量，必须与数据库中的片段向量使用同一套生成规则，相似度比较才有意义。

举个例子：
1. 今天用模型 A，将“未发货可以退款”生成向量，存入数据库。
2. 明天服务背后换成了模型 B，但对外仍叫 Qwen3.5，也仍然输出 4096 维。
3. 此时问题用 B 生成向量，数据库正文却是 A 生成的向量。虽然维度一样，向量空间可能已经不同，检索结果就不可靠。

因此，规则变化后换一个 profile：

```text
旧数据：qwen35-4096-raw-v1
新数据：qwen35-4096-raw-v2
```

当前代码会在入库时保存这个标识，检索时通过：
```text
AND embedding_profile = 当前配置的profile
```

只检索同一套配置产生的数据。换了 profile 后，需要用新规则重新向量化并入库，旧 profile 的数据不会自动转换。

只有实际模型版本、向量维度或影响输入内容的预处理规则变化时，才需要更换。日常新增文档、文档修订，以及模型保持一致时更换服务地址或 API Key，都可以继续沿用原 profile。


### 实体类
```java
@Data
@TableName(value = "public.kb_chunk", autoResultMap = true)
public class KbChunk {
    
    /** 原文定位信息，例如章节路径、页码和起止行号；保存为 JSONB 对象，默认值为 {}。 */
    @TableField(typeHandler = JsonbTypeHandler.class)
    private Map<String, Object> sourceLocator;

    /** 业务扩展属性，例如标签、业务分类和语言；保存为 JSONB 对象，默认值为 {}。 */
    @TableField(typeHandler = JsonbTypeHandler.class)
    private Map<String, Object> metadata;

    /** 片段的单精度浮点向量，默认约定为 4096 维，处理中可为空；查询向量须使用相同配置。 */
    @TableField(typeHandler = VectorTypeHandler.class)
    private float[] embedding;
    
}

```

`TypeHandler` 负责 Java 字段类型与数据库字段类型之间的转换，在 MyBatis 读写数据库时使用。

普通的 Long ↔ bigint、`String ↔ text`，MyBatis 已经有内置处理器。我们这里还有两种特殊类型，因此补了两个处理器：

| 处理器 | Java 类型 | PostgreSQL 类型 | 对应字段 |
|---|---|---|---|
| `VectorTypeHandler` | `float[]` | `vector` | `embedding` |
| `JsonbTypeHandler` | `Map<String, Object>` | `jsonb` | `source_locator`、`metadata` |



## 文档读取和分块

上传一个 UTF-8 编码的 `.md` 文件，即可由服务端完成分片、向量化和保存。

当前 Embedding 使用 `VllmTextEmbedding` 对接 vLLM 的 `/v1/embeddings`。请求只包含 `model`、`input` 和 `encoding_format`，省略 `dimensions`，避免当前服务拒绝显式维度参数。`rag.embedding.dimensions=2560` 仍用于校验返回向量，不能通过这个配置改变模型实际输出维度。上传正文和检索问题共用这一实现；切换模型后需在新的 profile 下重新上传文档。

启动前确认数据库连接、向量模型地址及维度配置可用。现有配置校验要求 `rag.embedding.api-key` 和 `rag.chat.api-key` 非空；无需鉴权的本地模型服务可填写 `EMPTY` 占位。

```bash
# 从仓库根目录执行，只需要提交 file
curl http://localhost:8083/api/kb/chunks/upload-markdown \
  -F 'file=@rag-persistent/examples/after-sales.md'
```

默认 `tenantId=1`、`knowledgeBaseId=1`、`documentVersion=1`，文档 ID 由 MyBatis-Plus `IdWorker` 生成并返回。每次省略 `documentId` 都创建一份新文档。

需要指定知识库或更新已有文档时，可附加表单字段：

```bash
curl http://localhost:8083/api/kb/chunks/upload-markdown \
  -F 'file=@rag-persistent/examples/after-sales.md' \
  -F 'tenantId=1' -F 'knowledgeBaseId=100' \
  -F 'documentId=10001' -F 'documentVersion=1'
```

同一文档下一次修订沿用 `documentId` 并递增 `documentVersion`；重复提交相同业务范围、版本和 profile 会返回 409。

分片规则：

- 识别 `#` 到 `######` 的 ATX 标题，按章节划分，保留标题与正文；代码围栏中的 `#` 不视为章节。
- 每片最多 2000 个 Java 字符，长章节优先在换行处拆分，单行过长时继续截断；字符数量不等于 Token 数，`token_count` 保持为空。
- 当前采用不重叠的简单分片，不是完整 Markdown AST 解析器，不识别 Setext 下划线标题等全部语法。
- 去除 UTF-8 BOM，统一 CRLF/CR 为 LF，并裁剪每片首尾空白；内容指纹基于最终片段正文计算。
- `source_locator` 保存 `section_path`、`line_start`、`line_end`，行号从 1 开始；`metadata` 保存文件名和分片规则版本。
- 单个文件最大 1 MiB，最多 200 片；空白正文、非 `.md` 文件、非法 UTF-8、空字符或片段数量超限返回 400，文件过大返回 413。所有内容检查及分片完成后才开始数据库登记。

返回包含 `tenantId`、`knowledgeBaseId`、`documentId`、`documentVersion`、`filename`、`chunkCount` 和 `chunks`。`chunks` 列出每片的 `id`、`chunkNo`、`status`、`errorMessage`；HTTP 200 仍需检查是否存在 `failed`。

这里只把分片保存到数据库，原始附件不另存磁盘。`source_uri` 中的 `upload:文件名` 是上传来源标识，不是可下载的文件地址。

## 向量的存储与更新

按以下顺序阅读，可以跟踪一个上传片段从 HTTP 请求到 pgvector 的过程：

```text
KbChunkController.uploadMarkdown
  → MarkdownUploadService.upload：校验文件、严格 UTF-8 解码、确定文档归属
  → MarkdownChunker.split：按标题和长度分片
    → KbChunkService.ingest：构造 KbChunk，计算 SHA-256，设置 pending
        → KbChunkMapper.insert：MyBatis-Plus BaseMapper 生成 INSERT，回填自增 id
    → KbChunkService.embed：AgentScope 生成向量并校验维度
        → KbChunkMapper.markReady：XML SQL 写入 embedding、embedded_at、ready
        → VectorTypeHandler：把 float[] 绑定成 PostgreSQL vector 参数
```

一个片段对应 `kb_chunk` 中一行数据。原始信息先在短事务中登记，提交后逐片调用模型，向量化成功的片段立即可检索；失败则通过 `markFailed` 记录为 `failed`。这是同步处理接口，没有后台任务或自动重试。

`insert` 使用继承的 `BaseMapper` 方法，因此没有额外手写 INSERT SQL。`markReady` 的 SQL 位于 `src/main/resources/mapper/KbChunkMapper.xml`，核心更新如下：

```sql
UPDATE public.kb_chunk
SET embedding = ?, embedded_at = CURRENT_TIMESTAMP,
    status = 'ready', error_message = NULL
WHERE id = ? AND status = 'pending' AND deleted_at IS NULL;
```
